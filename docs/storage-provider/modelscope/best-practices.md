# 最佳实践

本文档给出 Cloudreve ModelScope 存储策略的推荐配置与使用方式。踩坑清单见
[pitfalls.md](pitfalls.md)，接口细节见 [api.md](api.md)。

## 1. 部署前

- 仓库必须**已存在且有写权限**，驱动不会自动创建仓库。
- 访问令牌在魔搭账号设置中创建，填入策略的「访问令牌」。令牌在服务端使用，
  不会下发给浏览器。
- 修订版本默认 `master`。Cloudreve 不做额外限制，任何分支名都可以（校验只要求
  `^[A-Za-z0-9_.-]+$`）。历史上 `datasets` 曾被建议只用 `master`，因为早期实现使用的
  删除端点缺少 `Revision` 参数；Cloudreve 已改用 commit 删除 action，不再有这个约束。
- 命名空间是**两位数字**（`00`–`99`），它是物理路径的分片维度，见第 3 节。

## 2. 配置

创建向导暴露以下字段（`ModelScopeWizard.tsx`）：

| 字段 | 说明 | 默认值 |
|---|---|---|
| 策略名称 | Cloudreve 内部标识 | — |
| 仓库 ID | `owner/repo` | — |
| 接入点 | ModelScope origin，必须 HTTPS | `https://www.modelscope.cn` |
| 访问令牌 | 上传时必需 | — |
| 仓库类型 | `datasets` 或 `models` | `datasets` |
| 命名空间 | 两位数字 | `00` |
| 修订版本 | 提交目标分支 | `master` |

### 后端强制项

`service/admin/policy.go` 的 `normalizePolicy()` 会强制以下不变量，前端无法覆盖：

- **`relay = true`（上传中转恒开）**。对象路径由内容 SHA-256 决定，内容读完前无法命名
 上传目标，因此上传一律经服务端中转。这不是可调选项。
- `server`、`bucket_name`、`secret_key` 必填。
- `repo_type` 只接受 `models` / `datasets`。
- `namespace` 必须匹配 `^[0-9]{2}$`。

## 3. 物理路径与命名空间

对象路径固定为：

```
<namespace>/<sha256[:2]>/<sha256[2:]>
```

例如 digest 为 `30298d9a8d…`、namespace 为 `00`：

```
00/30/298d9a8dd621809fba0a8b83f1cff0d625427b71770d5a05067142fae4b9ec
```

设计后果：

- **内容寻址**：相同内容映射到同一路径，重复上传是 no-op，实体共享同一份字节。
- **目录树不在上游**：文件名、目录结构、文件大小等元数据全部保存在 Cloudreve 数据库，
  上游只有 blob。因此驱动不实现 `List`。
- **namespace 是分片维度**：同一个仓库下，不同 namespace 的对象路径天然隔离。多实例
  共用一个仓库时用不同 namespace 分片，避免相互踩踏。

## 4. 上传

### 4.1 让客户端先算好 hash（推荐）

ModelScope 策略会向客户端声明 `client_hash_required = true`
（`service/explorer/response.go`），前端据此在创建上传会话前**在浏览器本地**计算整个文件的
SHA-256（`Uploader/core/uploader/base.ts` 的 `hashFile`），并随会话请求提交为 `client_hash`。

此时驱动走**流式直达**路径（`putStreamed`）：

- 内容边读边转发到存储，不落盘，内存占用与文件大小无关。
- 读到一半即开始上传，不必等整个文件读完。

这是大文件应当走的路径。`client_hash` 缺失时驱动无法预先寻址，只能回退到临时文件，
所以**不要让客户端跳过 hash**。

### 4.2 没有 hash 时回退到临时文件

若客户端无法预先计算摘要，驱动会先把整个请求体写入临时文件以求得 digest，再上传
（`putBuffered`）。文件大小决定临时磁盘占用，因此**大文件应确保客户端提供 hash**。

### 4.3 小文件走内联

≤ 5 MiB 的对象不作为 LFS blob，而是以 base64 内联进 commit 请求
（`putInlineStreamed`）。这类对象：

- 没有独立 URL，`HasPublicSource` 返回 `false`。
- 只能经服务端读取，无法生成直链。

这是下载模式下必须回退到中转的根因。

### 4.4 内容已存在时不传内容

服务端在建会话时就用客户端声明的摘要探测一次：若对象已在仓库中引用，或已存在于上游
存储，会话直接标记为 **prevalidated**，客户端**不发送任何内容**，上传立刻完成。

- 只有 `client_hash` 存在且对象不是内联小文件（> 5 MiB）时才探测。
- 探测失败不阻断上传，只是退回正常传输。
- 这条路径不重新校验内容——见 [pitfalls.md](pitfalls.md#坑-13已存在对象不传内容就不重新校验)。

### 4.5 内容校验

走内容接收路径时，服务端会独立计算 SHA-256 并与声明值比对：

- 长度不符 → 报错，不提交。
- 摘要不符 → `ErrDigestMismatch`，不提交。

由于路径由 digest 决定、且对象在实体间共享，接受不匹配会把内容归档到描述其它字节的
路径下，所以这里没有放宽选项。

## 5. 下载

两种模式：

| 模式 | 行为 | 适用 |
|---|---|---|
| **中转**（`internal_proxy = true`，默认） | 字节经 Cloudreve 转发 | 需要即时撤权、或对象为内联小文件 |
| **直链**（关闭 `internal_proxy`） | 302 到上游签名 URL | 节省服务器带宽 |

### 直链的代价

签名 URL 一经签发即为 bearer 凭证：在 `auth_key` 过期前，持有者可继续下载，**即使本地
已删除该文件或已撤销访问**。因此：

- **不要对敏感文件启用直链。**
- 严格撤权需求只能用中转模式。

### 自动回退

即使关闭了中转，内联小文件（≤ 5 MiB）仍然只能经服务端转发——上游直接返回内容而非
重定向，驱动返回 `ErrNoPublicUrl`，由服务端接管。这条回退是自动的，不额外多一次请求。

## 6. 验证清单

上线前至少确认：

1. 用 `master`（或其他有效分支）作为修订版本创建策略并保存成功。
2. 上传一个 > 5 MiB 的文件，确认在 Cloudreve 中可见且可下载。
3. 上传一个 < 5 MiB 的文件，确认下载走中转（内联对象无直链）。
4. 若启用直链下载，确认大文件返回 302 且浏览器能直接取到内容。
5. 删除文件后确认上游路径消失。
