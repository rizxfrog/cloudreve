# ModelScope 存储策略

Cloudreve 的 ModelScope 存储策略把**文件内容**存放在魔搭（ModelScope）仓库中，文件名、
目录树等元数据保留在 Cloudreve 数据库。物理对象按内容 SHA-256 寻址。

适用代码：`pkg/filemanager/driver/modelscope/`。

## 一分钟速览

- **只存字节**：目录树与元数据在数据库，上游只有内容寻址的 blob。因此没有 `List`。
- **上传必须中转**：对象路径由内容摘要决定，读完前无法命名上传目标；且上传地址需认证。
- **下载可直链**：读取路由 302 到 CDN 签名 URL，无凭证即可取内容。
- **路径布局**：`<namespace>/<sha256[:2]>/<sha256[2:]>`，`namespace` 是两位数字的分片维度。
- **≤ 5 MiB 内联**：小文件 base64 内联进 commit，没有独立 URL，只能经服务端读取。

## 最容易踩的三个

1. **direct 上传不可行、direct 下载可行** —— 结论相反，别一并处理。见 [pitfalls.md](pitfalls.md#坑-1direct-上传走不通direct-下载可以)。
2. **HTTP/2 上传慢 3 倍** —— 存储传输层必须钉到 HTTP/1.1。见 [pitfalls.md](pitfalls.md#坑-4http2-上传慢约-3-倍性能坑)。
3. **文件读取路由没有 `repos/` 段** —— 写错会得到 421 而非 404。见 [pitfalls.md](pitfalls.md#坑-5文件读取路由不带-repos-段误用返回-421)。

## 主要配置项

| 字段 | 默认值 | 说明 |
|---|---|---|
| 接入点 | `https://www.modelscope.cn` | 必须 HTTPS origin |
| 仓库 ID | — | `owner/repo`，必须已存在且有写权限 |
| 访问令牌 | — | 上传必需，绝不下发浏览器 |
| 仓库类型 | `datasets` | `datasets` 或 `models` |
| 命名空间 | `00` | 两位数字，路径分片维度 |
| 修订版本 | `master` | 提交目标分支 |
| 提交模式 | 直接提交 | 直接提交 / 排队提交 / 窗口合并提交，三选一且互斥，见下节 |
| 排队间隔最小值 / 最大值 | `3` / `5` | 仅排队模式，秒，随机范围 |
| 合并窗口最小值 / 最大值 | `3` / `5` | 仅窗口合并模式，秒，随机范围 |

上传中转由后端**强制开启**，不可配置。

## 提交模式

ModelScope 会拒绝间隔过短的连续提交（`commit rejected by repository policy`），批量上传时
很容易触发。策略提供三种处理方式，**互斥，只能选一种**：

| 模式 | 行为 | 适用 |
|---|---|---|
| **直接提交**（默认） | 每次 commit 立即写入 | 仓库允许连续提交 |
| **排队提交** | 所有 commit 逐个排队执行，相邻两次之间随机等待 | 写入持续但频率不高 |
| **窗口合并提交** | 随机窗口内到达的 commit 合并为**一次**仓库提交 | 短时间内突发多次上传 |

### 排队提交

- 该仓库的**每次** commit（上传、删除都会产生 commit）都提交到专用于此的队列
  `modelscope_commit`（可在「参数设置 → 队列」看到其实时指标），由队列逐个执行，同一时刻
  只有一个 commit 在途；
- 相邻两次 commit 之间插入一个**随机间隔**，可配置范围，例如最小值 `3`、最大值 `5`
  表示随机等待 3～5 秒；留空则使用默认的 3～5 秒；
- 间隔从前一次 commit **结束**时刻开始计算，因此一次慢提交不会让下一次立刻跟进。

提交串行化是必要的：ModelScope 的 commit 是整仓库无栅栏的写操作，两个在途 commit 可能互相
覆盖（见 [pitfalls.md](pitfalls.md#坑-7revision-不能当条件写栅栏)），逐个执行才能保证结果确定。

队列的调度参数（工作线程数、最大执行时间等）在「参数设置 → 队列 → 魔搭提交」中调整；工作
线程数超过 1 也不会破坏间隔，间隔由驱动侧按仓库统一控制。

> 从机节点（stateless）不运行该队列，驱动会在进程内串行并等待同样的随机间隔。

### 窗口合并提交

- 第一个 commit 到达时开启一个随机窗口，窗口内到达的所有 commit 被收集，窗口结束后作为
  **一次**仓库提交写入；
- 窗口时长随机取值于配置范围，例如 `3` 和 `5` 表示随机 3～5 秒；留空则使用默认的 3～5 秒；
- 同一对象在窗口内被提交多次只写一次；
- 一次合并最多 100 个 action（与回收站批量删除的批大小一致）或 32 MiB 内联内容（内联对象
  的 base64 正文按此计），任一到限即拆分为多次提交。

**调用方语义不变**：上传的 `Put` 仍会等待其 action 真正写入仓库后才返回，失败也会照常上报，
因此上传成功依旧代表内容已入库。区别只是等待时长变为「窗口剩余时间 + 提交耗时」。

同一仓库的合并窗口由进程内共享，因此并发的多个上传（各自持有独立的 driver）会合并到一起。

> **注意**：窗口合并**不使用**「参数设置 → 队列 → 魔搭提交」这条队列——合并发生在进程内按
> 仓库共享的合并循环里，从不产生队列任务。因此该队列卡片在合并模式下**各指标恒为 0**
> （从未有任务提交），这不是故障。只有**排队提交**模式会把 commit 送进该队列并推高其计数；
> 该队列的工作线程数等参数对合并模式没有影响。

窗口改动**无需重启**：窗口在每次开启新窗口时读取当前策略值，保存后从下一个窗口起生效
（已开启的那个窗口沿用它被创建时的时长）。

> **代价**：合并以延迟换请求数——窗口内每个调用方都要等到窗口结束。突发写入越密集收益越大；
> 若写入是稀疏散布而非突发，直接提交或排队提交更合适。

两种模式的区别：排队提交把 N 次提交摊开到 `N × 间隔`，窗口合并把窗口内的 N 次提交压成
1 次请求（所有调用方等待同一个窗口）。前者上限稳定、延迟可预期，后者请求数更少但延迟随
突发规模增长。
